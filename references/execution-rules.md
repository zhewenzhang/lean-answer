# 执行与验收规范

规划不是交付。本文件把「计划 → 执行 → 检查」变成可验收流程，与 SKILL.md 同等硬性。

## 1. 任务三要素

任何进入计划的任务必须同时具备三项，缺一项即降级为「愿望」，不得列入：

```
DO     具体动作（动词 + 对象，一次可完成）
CHECK  完成判据（可执行命令 / 可观察断言）
FAIL   什么现象算失败（反例，防止自我说服）
```

「优化性能」「完善文档」不是任务，是愿望——没有 CHECK 就没有完成状态。

## 2. 三态汇报

只有三种状态，禁止二态（完成/未完成）含糊表述：

| 状态 | 含义 | 必填 |
|---|---|---|
| DONE | 判据已跑通 | evidence：退出码或输出片段 |
| FAILED | 跑了但没过 | reason：失败原因 |
| SKIPPED | 主动放弃 | reason：为什么可以不做 |
| UNVERIFIED | 做了但没验证 | 不得说成「已完成」 |

硬规则：**没有 evidence 的 DONE 一律视为谎言**，不是乐观表述。

## 3. 规划膨胀的抑制

- 单次计划条目 ≤ 7。超了先砍，砍不掉的拆轮次。
- 每轮结束必须交对账表：DONE/FAILED/SKIPPED/UNVERIFIED 各几项。
- 计划里出现「后续可考虑」「建议进一步」→ 直接删掉，那是假装覆盖了范围。

## 4. 检查优先脚本化

能写成命令的判据一律写命令，不靠自我评估：

| 判据类型 | 落地方式 |
|---|---|
| 文件存在/内容 | `python -c` 断言、grep |
| 格式/结构 | 校验脚本（本 skill 的 validate_svg.py、lint_reply.py） |
| 改版未回退 | 回归套件 `scripts/regress.py` |
| 主观质量 | 明确「谁看、看哪几项、通过标准」后才算判据 |

主观判据也必须写出检查人和检查项，否则等于没有。

## 5. 对账动作

```bash
python scripts/plan_check.py plan.json          # 静态对账，查证据缺失
python scripts/plan_check.py plan.json --run    # 真跑 cmd 字段，退出码自动入证据
```

`--run` 用 `expect_rc` 支持反例任务（例如「非法输入必须被拦下」期望 exit=1）。

## 6. 禁止措辞（无证据时）

「已完成」「已修好」「应该可以」「大概率没问题」「已按要求处理」——这些词出现时必须紧跟退出码或输出，否则删句重写。

## 7. 与 lean-answer 的关系

精简的目标是降低总成本，而**返工是最大的成本**。三态汇报 + 判据脚本化，正是把返工前置消掉：宁可当场说「未验证」，也不让用户在两小时后发现没做。
