# 任务模式与检查机制

同一套检查，在两类任务里的呈现方式必须相反：**交付型把检查藏进成品，事务型把检查摆到台面**。搞反了就是现在最常见的病——交付物里塞满「我检查了 A/B/C」，而周期性任务只机械照做、从不确认结果。

## 0. 模式判定（一步）

```
用户要的是「一个东西」 → 交付型：报告、PPT、代码、表格、文案
用户要的是「一件事被办成」 → 事务型：发邮件、备份、同步、定时晨报、整理文件
```
周期性（自动化 / 每天 / 每周）任务**默认事务型**，无论产出长短。

## 1. 交付型：隐性验证

- 验证在交付前完成，**不写进回复**。不列「已检查格式 / 已核对数字 / 已校验边界」——那是把内部工序当成果。
- 只交付成品 + 必要的使用说明。检查痕迹最多留一处：影响结论的重大偏差，用一句说明，不是清单。
- 失败就明说哪里没达标，不假装完成（此时允许一句技术说明，仍不铺开）。
- 「做成功」判据：接收方能直接用——能打开、能解析、数字口径一致、结论有依据。

## 2. 事务型：显性确认

每轮固定三段，各一到两行，不铺陈：

```
结果  目标状态是否达成（给数字）
检查  判据怎么验的（给命令/来源，一行）
差异  与上轮相比变了什么；异常则给根因 + 本轮修正动作
```

四条硬规则：

- **空结果必须区分两种情况**：「确实没有新内容」与「读不到来源」。后者是失败，不是「无更新」。定时任务最典型的静默失败就死在这里。
- **异常处理阶梯**：诊断根因 → 换方法重试一次 → 仍失败则报障并降级或暂停。**禁止第三次原样重跑**。
- **每轮留台账**：用 `scripts/runlog.py` 记录状态与签名（sig），下一轮能回答「这次和上次有何不同」。
- **检查逻辑本身要被迭代**：每轮记一句「本轮检查漏掉了什么」，补进下一轮判据。检查不进化，错误就会复利。

## 3. 「做完了」与「做成功」

| | 做完了（动作发生） | 做成功（目标达成） |
|---|---|---|
| 备份 | 上传命令执行过 | 云端存在同名文件且字节数一致 |
| 晨报 | 摘要文本生成了 | 两个来源都有内容或明确说明「确实无更新」 |
| 发邮件 | 发送接口返回 200 | 收件人地址正确、附件在场、无退信 |
| 制图 | SVG 画完了 | 校验器 exit 0，人眼确认不被裁切 |

判据一律写成「可观察的目标状态」，不写「执行了某动作」。动作是手段，状态才是交付。

## 4. 周期任务在定义阶段就要内建检查

任务 prompt 必须含 CHECK 段，缺它不许建排程：

```
CHECK  本轮成功的可观察特征（数量、覆盖来源、文件名/字节数）
异常   什么现象算失败（来源为空、条目数骤降、文件名不符）
失败   异常时怎么办（诊断项、重试方式、升级条件）
```

没有这段，模型只能把定时指令读成「照做」——它不是懒，是没被告知「做完」长什么样。

## 5. 防重复犯错：升级闸门

```
第 1 轮异常 → 诊断根因，换方法重试
第 2 轮同因 → 台账标记，报障：已连续 2 轮同一原因失败
第 3 轮      → 禁止原样重跑；必须改方案或暂停任务，等用户决策
```

`runlog.py` 会自动做这个判定：末尾连续两轮同 status + 同 sig 即输出 ESCALATE 并返回退出码 1。
